# 12 — Feed Loading Strategy

**Last updated:** 2026-08-24

---

## What the Home Feed Is

A **mixed discovery feed** generated by `generateDiscoveryFeed` (`src/services/feedGenerator.ts`) — a pure function over already-fetched data. It is **NOT** a rigid Companion → Event → Activity pattern.

## Composition Rules

1. Companions grouped by interest category; categories shuffled, top N selected (`categoriesPerFeed`)
2. Within each category, content types are mixed: companions + category-matched activities, events, stories, posts
3. Per-type caps prevent domination: companion 30% · activity 20% · event 20% · story 15% · post 15%
4. Deduplication by ID across the whole feed
5. Scoring by location/category/freshness for activities & events

## Stability Guarantees (non-negotiable)

- **Existing displayed content must remain stable.** New data arriving from Firebase must NOT randomly reorder content the user has already seen.
- Content must not visibly disappear and reappear between renders.
- Refresh may vary *which* items are picked and *section ordering* (intentional discovery behavior, covered by tests CASE 7/8), but within a session, appended content is append-only.

## Loading Pattern (the only allowed pattern)

```
Initial small batch
        ↓
User scrolls near end (sentinel, +200px buffer)
        ↓
Load next small batch
        ↓
APPEND
```

Progressive reveal: desktop `DiscoveryFeed` (`visibleCategoryCount`) and mobile `ClientApp` (`visibleMobileCategoryCount`) both start at 2 category chunks and increment by 1 as the sentinel enters the viewport.

## Prohibited

- Loading hundreds/thousands of records immediately
- Repeatedly reloading the entire feed
- Randomly reordering existing content when new Firebase data arrives
- Causing visible content to disappear and reappear
- Creating unnecessary real-time listeners for feed data
- Fake/seeded feed content in production flows

## Real-Time vs Pagination

- **Real-time listeners** (meaningful value only): messaging, notifications, booking status, presence
- **Pagination**: all large discovery collections (companions, posts, stories, activities, events)

## Current Implementation Status (honest)

| Aspect | Status |
|---|---|
| Mixed feed generation + type caps | ✅ implemented + tested (feed-generator.test.ts, 15 cases) |
| Progressive reveal (desktop + mobile) | ✅ implemented (IntersectionObserver + scroll fallback, 200px root margin) |
| **True cursor pagination (`startAfter` on document ID)** | ✅ implemented in `useFirestoreData` hooks — one-shot paginated fetches, append-only merge by ID, session cache, shared in-flight request dedup; discovery collections no longer use live listeners |
| Feed stability across batches | ✅ implemented via `stabilizeFeed` (`src/services/feedStabilizer.ts`) — previously displayed items keep their exact relative order; new items append within their category chunk; tested in home-feed-performance.test.ts |

## Pagination details

- All six Home collections paginate by **document ID** (`orderBy(documentId())`, cursor = last doc ID). This needs only automatic single-field indexes — **no new composite indexes required**.
- Page sizes: companions 15, stories/activities/events/partners/community_posts 10.
- Discovery data is fetched once per session and cached in memory (module-level session cache); remounts reuse it without refetching. localStorage provides instant cold-start paint before the first batch merges.
- Real-time listeners were removed for all discovery collections per the rules above; messaging, notifications, and bookings keep their listeners.
