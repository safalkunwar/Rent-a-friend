This local slice makes the existing wallet entry honest, establishes exact integer denomination helpers, and validates bounded funded-reward campaign schedules. It does **not** qualify a production wallet or activate Coin movement.

## Delivered

- Replaced the generic wallet-unavailable card with a Coins panel that explains the planned reference denomination (10 Coins = NPR 1), reads only a server-verified owner balance, and distinguishes no wallet from a verified zero balance.
- Added an authenticated `getCoinWallet` callable. It derives the UID from Auth, returns only allowlisted fields from that UID's wallet and at most 20 statement rows, and does not accept a requested UID. The client validates the callable response and never reads or writes wallet documents directly.
- Isolated the owner read in a bounded server helper and added tests for no-wallet behavior, owner scoping, statement allowlisting, query cap, frozen/malformed projections and malformed UIDs.
- Added a welcome-grant check action backed by the authenticated retry callable. On grant it refreshes the wallet from the server. Purchase, transfer, and cash redemption remain unavailable; no transfer is offered.
- Added pure `coinsToNprPaisa()` and `nprPaisaToCoins()` helpers. They use integer arithmetic, reject fractional/negative/unsafe values, reject paisa values not exactly representable as whole Coins, and guard converted overflow. The documented 5,000-Coin cash threshold is a constant only; cash redemption remains off.
- Added policy-neutral reward contracts: a bounded parent-first ancestry snapshot must be unique, acyclic with respect to the invitee, and strictly ordered by trusted signup ordinals; reward records must have valid whole-Coin amounts, a source funding reference, policy/version metadata and a level no greater than five. A Web Crypto SHA-256 helper derives stable reward IDs from economic source, beneficiary and reward kind, excluding mutable policy/version/level fields.
- Added a pure funded-campaign budget planner. Each allocation requires an explicit whole-Coin amount, a finite campaign grant cap and a per-beneficiary cap. It calculates worst-case campaign and per-beneficiary liability using integer paisa arithmetic, rejects duplicate allocations and schedules above budget, and allows only activity-owner or direct-referrer recipients (never multilevel referrals).
- Extended the Phase 3 pure ledger contract with exact inverse-journal construction and validation for a source reversal. This is input validation only; durable one-time reversal, authorization and concurrent duplicate prevention still require the ledger writer and reconciliation path.
- Added focused UI, conversion, referral-chain, reward-envelope, stable-ID and campaign-budget tests.

## Server-side grant candidate

An internal Functions transaction implements the grant against a versioned campaign pointer, immutable policy, dedicated funded allocation, campaign counters, reward receipt, balanced COIN journal, wallet projection, provenance lot and owner statement. It keys the reward by Auth UID, enforces a per-UID grant idempotency key and finite campaign cap, and handles retries. The 2026-10-19 implementation also requires an approved identity case, a private UID/person record and a first-approved-UID HMAC claim in the same grant transaction. `onUserCreate` no longer issues Coins; `claimWelcomeCoins` is the grant entry point. A retry verifies the retained campaign policy and complete prior artifact set before returning `ALREADY_GRANTED`; partial or conflicting records fail closed. The server environment gates default off, and no active campaign pointer means no award.

This is not live: code now rejects campaign policies that do not use the owner-approved 100-Coin amount, while the campaign must still carry approved dates, NPR budget, grant cap, Auth account qualification, finance approval reference and dedicated funded allocation. Missing policy/funding documents and the default-off server gate prevent issuance. The retry/read callables and client panel are local code only; no Function was deployed. No profile-unlock spend path or matching wallet rules are released. A temporary, checksum-verified Microsoft JDK 21 runtime was used for local emulator acceptance; the system Java installation and global environment were not changed.

## Profile-unlock entitlement and spend candidate

A local `requestCompanionProfileUnlock` callable and `profileAccess` client helper now exercise the proposed full-profile path without adding UI or direct client database access. The backend derives the viewer from Auth, checks server-owned viewer/provider access records, canonical provider identity and approved KYC linkage, and bilateral blocks. It grants up to five distinct free profiles per Kathmandu calendar day, serializes quota races, and records one durable viewer/provider entitlement. Reopening an entitlement is free. After the free quota, paid unlocks require both `SATHI_PROFILE_UNLOCK_COINS_ENABLED=true` and an immutable approved `coin_profile_unlock_policies/profile_v{version}` selected by the server pointer. A paid grant atomically debits the wallet, consumes oldest backed non-cash lots, writes a balanced COIN journal and owner statement, stores the entitlement, and records replay state. The candidate fails closed on corrupted source journals, wallet/lot mismatch, or more than 20 open lots; consolidation is required before spending in that case.

The candidate is not active or policy approval. The proposed 50-Coin amount is not hard-coded; no policy pointer or funding record is present; the paid feature flag defaults off; wallet client rules and the profile UI integration are not released. Free entitlement candidate checks are also not Phase 2 production qualification. The new lot query requires the `lots` composite index in `firestore.indexes.json`; it has not been deployed or checked for live readiness. No Function, index, rules, or data were deployed or changed in Firebase.
