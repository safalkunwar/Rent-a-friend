# Firestore contract registry and migration map

Target design v1, 2026-09-09. This is not a live collection census or permission grant. No listed new collection should be created before its implementing phase. Existing source paths are relative to repository root. Current/deployed divergence is documented in 20; 21 defines actor permissions. Every write authority below is backend unless a bounded existing client contract is expressly retained.

## Common contracts

N=new, E=extend existing, P=preserve, A=compatibility adapter. Document path ID overrides stored id. New authority timestamps are server Timestamp; all records have schemaVersion, createdAt, updatedAt unless immutable (createdAt only). Mutation versions are integers, never last-write-wins for financial/approval transitions. IDs are UID, random UUID, or validated deterministic hashes of declared keys. References are typed `{kind,id}` or named UID/ID fields, never untrusted arbitrary paths. Public projections carry sourceVersion and generatedAt; only one backend owns each projection.

R scopes: PUB=eligible public projection; SELF=subject UID; PARTY=canonical transaction participants; TENANT=active membership and permission; REVIEW=assigned reviewer; OPS=assigned operation/case permission; FIN=finance permission/minimized view; SERVER=no direct clients. W=B=trusted backend command; U=owner bounded editable fields; L=existing locally/prod-tested client transaction retained only for its proven version. No public doc contains private fields requiring field redaction. D=soft delete unless approved retention job. Client admin is not B.

Retention classes: ACCOUNT=life of account plus approved deletion/appeal; PUBLIC=owner deletion/moderation then bounded cleanup; VERIFY=private credential retention by approved policy, legal hold overrides; FINANCIAL=immutable required audit period (proposed7years, legal/provider approval required); OPS=case policy (proposed90days after closure, hold overrides); EPHEMERAL=explicit expiresAt plus guarded cleanup; LOCATION=proposed7days after trip, hold overrides. No automatic deletion from these proposed periods until approved. Expiry checks are immediate authorization; TTL is cleanup only.

## Exact query/index plan

Each proposed ordered query has limit<=50 unless stated; cursor includes final `__name__` in same final direction. `=` denotes ASC equality-index field, `[]` ARRAY_CONTAINS, arrows order. Collection scope unless explicitly a parent subcollection. Implement only index needed by current phase; no mass speculative deployment. Single-field/direct queries use automatic indexes. Disjunctions/multiple array filters are not assumed supported by one index.

The index column also declares required projection/queue fields: e.g. public agencies/partners carry derived primaryServiceAreaId; financial queue records carry status/updatedAt; rewards carry status/vestAt; review visibility uses moderationStatus. Pure schema validation must require every queried field before publishing that schema version. Queries must not silently exclude incomplete legacy records: use the documented compatibility reader until the bounded backfill is verified.

## Migration and schema ownership

Legacy field adapters: users.role display only; companion isVerified is historical reviewed claim, not independent badge; categories→interests by explicit reviewed mapping; companionId!=UID requires crosswalk, no implicit reassignment; booking v2 confirmed is unpaid acceptance; ISO timestamps converted per-domain with strict parser and update-time precondition, not collection-wide blanket rewrite; embedded reviews never automatically verified; documentFileUrl private path retained as compatibility name while adding storagePath; events participants arrays/nested docs not active membership truth; legacy diamond narrative maps to no starting Coin balance. Never mint opening balances from demo metrics.

Every migration: dry-run by default, project assertion, exact cohort/document list, redacted report, backup/restore test, schemaVersion marker, compare-and-set updateTime, idempotent per-record operation, checkpointed bounded pages, verification counts and no delete initially. Dual-read means version adapter over one selected authoritative record, not union of divergent financial histories. Single writer by version/cohort; freeze relevant new writes if cross-version invariant cannot be maintained. Rollback disables new creation and restores compatible reader/previous config; never roll back ledger by deleting journals or deploy old rules that allow financial client writes. Historical immutable schema readers remain available after rollout.
