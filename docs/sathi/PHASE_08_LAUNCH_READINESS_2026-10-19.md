## Verified implementation

- Welcome grants use the canonical Firebase Auth UID for both the wallet document and deterministic reward ID. The transaction atomically creates the reward receipt, balanced COIN journal, non-cash lot, owner statement, wallet projection, campaign counter and funding decrement. The product amount is validated as exactly 100 Coins; the beneficiary maximum is one. The account-creation timestamp must fall within the approved campaign window, and disabled Auth accounts fail eligibility.
- A duplicate trigger/callable request returns `ALREADY_GRANTED` only after validating the prior campaign policy and all corresponding records. Missing or conflicting prior records fail closed. Emulator tests exercise same-UID concurrent requests, cap races, budget exhaustion, replay and conflicting-journal rejection.
- The welcome path requires `SATHI_WELCOME_COINS_ENABLED === "true"`, a current campaign pointer, an approved immutable policy, a finite cap, budget bounds and a funded allocation. The local grant transaction now also requires `SATHI_WELCOME_IDENTITY_ENABLED === "true"`, an Admin-approved case, a server-only identity record and a person-claim marker owned by that UID. Both flags remain unset/off locally. Production `firebase functions:list --project hamrosathi1` previously returned only the seven media Functions; no Coins or identity Functions are deployed.
- The Auth-create trigger no longer issues welcome Coins. `claimWelcomeCoins` is the sole local grant entry point and its transaction fails closed until approved identity case/private records and the HMAC person claim match the authenticated UID. Existing reward, wallet, ledger, campaign cap and funding writes remain atomic. This fixes the prior signup-before-review defect in local source.
- Existing `companion_applications/{appId}.kyc.verificationStatus` is Companion-only and coupled to companion application approval/public profile activation; `VITE_COMPANION_REVIEW_ENABLED` defaults off. It does not cover ordinary customers or establish a universal claimant verification/dedup record. The existing companion review flow is not a qualified P8 integration.
- The new nested welcome-KYC Storage path allows owner upload of bounded JPEG/PNG/PDF evidence, reviewer reads, and root-admin deletion. Automatic retention cleanup, legal-hold administration and account-deletion handling are not implemented; raw evidence must not be collected in production until those controls and privacy/counsel approval are complete.
- The claimant upload client now deletes files only when upload itself fails before a case submission begins. If a callable response is ambiguous after submission, it preserves the files and refreshes case status, avoiding a committed case that points to deleted evidence. Focused tests cover both cleanup and preservation paths.
- Client wallet access goes through `getCoinWallet`, which derives the UID from callable auth and returns a minimized projection. Local `firestore.rules` has no wallet or ledger allow rule, so direct client reads/writes default-deny. The Firestore emulator test verifies client read denial and now also checks client wallet creation/update and forged ledger creation are denied.
- Welcome lots/rewards are marked `cashEligible: false`. The wallet panel marks Add Coins, Exchange Coins, spending and cash redemption unavailable. There is no `addCoins`, `exchangeCoins`, transfer or cash-redemption Functions export. No referral reward producer is active in the current Functions source.

## Multiple-account abuse and verified-person decision

UID idempotency prevents repeat grants to one Firebase account, not one person. A user can create multiple UIDs and potentially claim once under each eligible UID. The finite campaign cap limits the maximum liability but does not prevent account farming.

The owner selected verified-person eligibility for **every welcome-Coin claimant, including customers**, and decided the grant cap is one per verified person across all Auth UIDs. Acceptable IDs are limited to a Nepali citizenship certificate, National ID, or passport. Remote claimant-to-ID matching requires a fresh selfie. Enhanced identity/liveness checks may be used only when justified and after privacy, legal, and technical review. The owner proposed a 30-calendar-day appeal window starting when the claimant is notified, an independent reviewer, senior escalation, and reconsideration for rejected cases. Raw evidence should be deleted within 30 days after the appeal window closes, or within 30 days after the final appeal decision if appealed; deletion should use a restricted, audited process and documented legal holds/applicable retention duties must be honored. Companions also require government ID and Guides require a trekking certificate. The owner selected `kyc_reviewer` for review, a different reviewer for appeals, and `super_admin` for escalation. Remaining: deletion-job authority/legal-hold mechanics, disclosure, and Nepal counsel approval. **The claimant ID/selfie gate is implemented locally behind default-off gates; no evidence was collected and no production activation occurred.** Incomplete profiles can remain eligible only if the required ID review can be completed without completing unrelated profile fields.

| Option | Abuse resistance | Trade-offs and privacy/fairness impact |
| --- | --- | --- |
| Keep UID-only eligibility; enforce a finite funded cap and monitor | Low against a person creating many accounts; hard cap bounds total campaign loss | Lowest friction and data collection. Accepts more Sybil exposure; early claimants may exhaust a capped campaign before legitimate users can claim. |
| One-time third-party person verification, storing only a signed result/token | Potentially stronger if provider can reliably de-duplicate people and bind the result to the Auth UID | Vendor cost, false rejection and provider dependence; requires disclosure, security review, data-processing terms, retention rules and counsel review. Raw ID retention may be avoidable but must be verified. |
| Human review of an accepted identity document | Can support person matching and exception handling | Highest sensitive-data and staff burden; breach/insider risk, slower access, language/document barriers and inconsistent decisions. Requires strict access logs, retention/deletion, appeals and trained reviewers. |
| Verified phone plus App Check/rate limits/device or IP velocity signals | Useful against basic automation; weak proof of a unique person | Shared/recycled phone numbers and shared networks create false positives; device/IP signals add tracking and retention concerns. App Check/rate limits do not solve multi-account abuse alone. |

**Current decision:** one grant per verified person across UIDs; use only citizenship certificate, National ID, or passport; require a fresh selfie; start the 30-day appeal window when the claimant views the decision; use a different `kyc_reviewer` for appeals and `super_admin` for escalations. Local implementation now uses first successful approval to reserve a person key to that UID. Code is gated off and requires Firebase App Check. Raw evidence cleanup, legal-hold operations, privacy/counsel approval, recovery, disclosure and production operations remain incomplete. Campaign caps and monitoring remain necessary even with identity checks.

**RBAC mapping:** the owner confirmed `kyc_reviewer` for initial review and a different `kyc_reviewer` for appeal; `super_admin` resolves escalations. The existing RBAC grants read/write KYC to `kyc_reviewer` and `super_admin`, and read-only to `platform_admin`. Explicit reviewer assignment, recusal and case-load controls remain unresolved; currently any qualified reviewer can see the queue, while the callable enforces different actors on appeals.

**Cross-account person-key design (built locally, not activated):** claimant submits an accepted document and fresh selfie into a case bound to their Auth UID. A `kyc_reviewer` records the decision; appeal requires a different reviewer, with `super_admin` escalation. The reviewer enters the document number transiently; backend normalization applies NFKC, trim, uppercase and removes whitespace/hyphens, then computes a version-1 HMAC using `SATHI_WELCOME_IDENTITY_HMAC_KEY` bound as a Functions secret. Raw numbers are not stored or logged by the implementation. A server-only person-claim record reserves the key to the first UID completing approval. Grant issuance atomically checks the verified case, private UID/person key, person claim, campaign/funding policy and existing reward state. Retries are idempotent; another UID receives only a generic identity-review-required result; concurrent approvals serialize through the person-claim transaction. Client rules deny access to private person-key and claim records.

The fingerprint is **linkable sensitive/pseudonymous data**, even though it is keyed. Local code now implements the approved normalization and version-1 HMAC but not key rotation, marker expiry/deletion, or recovery/transfer. The secret is not configured. Retention must preserve one-person deduplication after raw evidence deletion, with an approved lifecycle and legal-hold process. False matches can appeal and be reconsidered by a different reviewer; account recovery should restore access to the original UID's grant, while transfer/reissuance remains unimplemented. Privacy/Nepal-counsel review, data disclosure, retention/cleanup, hold authority, key rotation, recovery operation and campaign funding/release approvals remain required. Keep both identity and welcome-grant flags off.

## Technical blockers found

1. **Identity handling is locally implemented but not cleared for production.** Signup no longer grants. Callable grants require an approved UID-bound identity case and person claim inside the grant transaction. Claimant upload, status, appeal, reviewer, HMAC and Admin queue code exist behind default-off gates. Privacy/counsel approval, App Check production readiness, key rotation/retention, legal-hold and cleanup operations, reviewer assignment and account-recovery policy remain unresolved.
2. **Unapproved profile-unlock callable has a free-grant path before its paid Coins gate.** `requestCompanionProfileUnlock` is exported in local Functions source. `grantProfileUnlockWithCoins` grants up to five free daily profile entitlements before checking `SATHI_PROFILE_UNLOCK_COINS_ENABLED`; that flag protects paid spending, not all profile entitlements. The callable is absent from the current production Functions list, so this is not a current production exposure. Because the five-free entitlement policy and exact profile fields remain unapproved, do not deploy this callable. A safe source fix would add a separate default-off gate around *all* profile unlocks or otherwise prevent its deployment. That changes user-visible entitlement behavior, so owner approval is required before implementation.
3. **Reversal/vesting is incomplete.** Welcome grant policy currently accepts only `postingMode: "IMMEDIATE"`; the grant writer has no durable one-time reversal or reconciliation workflow. The Phase 3 inverse-journal helper is a pure contract, not an authorized persistent writer. Finance/product/counsel must decide the posting and reversal policy before engineering can complete that dependency.
4. **Production release scope is undefined.** The new Functions are local only. `onUserCreate` still initializes user profiles/custom claims, but no longer grants Coins; any deployment scope must be reviewed as a whole. Candidate exports include identity-review callables, `claimWelcomeCoins`, `getCoinWallet`, and the unapproved `requestCompanionProfileUnlock`; do not deploy a broad Functions bundle. Blaze status and exact Functions/config/source/rollback approval are not verified.
